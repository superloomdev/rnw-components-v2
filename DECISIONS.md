# Decisions

This file and `data/roster.json` are the only places in this repository, outside `_test/`, where the names Carbon, Material and IBM may appear. Component source never names a design system. Anyone changing this library reads this file first; anyone adding a rule adds a numbered row here, never a comment in a component.

## The idea

This is one generic React Native Web component library. A component owns its anatomy (which parts exist and how they nest) and its behavior (state, keyboard, focus, accessibility) and nothing else. Every value it draws - color, spacing, size, type, radius, border, focus ring, motion, shadow - is a token read from the theme. Every discrete shape choice - how a press is shown, where a field label sits, whether a border is drawn on one side or four - is an enum token the theme picks and the component implements every value of. Every glyph is an icon token whose value the theme carries as SVG path data. The library ships no colors, no font files and no icon files; a template supplies them all, and a sparse brand layer overrides a handful. A new design system is therefore a new template package and zero component changes, and that property is proven continuously by rendering the whole roster under three templates.

Carbon is the primary inspiration and the completeness checklist: every component of `@carbon/react` and `@carbon/react-native` has a row in the roster, and Carbon's rendered output is the measured reference for the anchor controls. Material is the second reference, used to keep the library generic - a shape that only Carbon has is designed so Material's shape fits the same anatomy, and where it cannot yet, the gap is recorded in the roster rather than hidden. The `default` template is neutral today and is the seed of the Superloom signature template - Carbon-inspired geometry, rounded corners, its own colors and an open-source icon set - which will be built later as a template alone, with no change to this library.

## Numbered decisions

Settled by the owner. Never reopened by an executor; amended only by a new row that names the row it replaces.

| # | Question | Decision |
|---|---|---|
| 1 | What is one component | Carbon's naming granularity: every `@carbon/react` and `@carbon/react-native` export is its own file with its own unit test. Spec, showcase entry, screenshot and doc page are per family (about 75 families). CSS-only exports (`ClassPrefix`, `usePrefix`) are marked `not_applicable` in the roster and not built. Every upstream export is accounted for in `data/roster.json`. |
| 2 | One library or two | One library. Numbers and colors are value tokens; discrete shape choices are enum tokens the theme picks and the component implements every value of; genuinely new anatomy is a library release plus a contract bump. Enum values are named by what they do (`ripple`, `underline`), never by a system. |
| 3 | How exact | Token values are proven once by the themer's parity oracles. Every component declares its geometry as token names in `spec.js` - no literals, enforced by the purity gate. The fifteen anchor controls are measured against the real rendered upstream component during their batch; the whole roster is measured in one pass before launch. A value Carbon never specifies uses a token from Carbon's own scale and is marked `superloom_decision`. |
| 4 | Shape differences | Six anatomy enums were added to the token contract in one bump before any component was written; Carbon is primary, Material is the reference for genericity. Where a Material shape is deferred, the component draws Carbon's shape with Material's tokens and the roster records the gap. Where neither system has an answer, the plainest anatomy wins. Deferred at launch: Material's clock-dial time picker and modal date picker. |
| 5 | Platforms | One file per component by default; platform APIs arrive through host-injected adapters; the roster records a platform answer for every row. A component that genuinely forks uses the three-unit split - `XWeb`, `XNative`, and a public `X` that is a dispatcher only - each half declaring its platforms as data; a missing half draws nothing, silently. No component other than a dispatcher may read the platform (gate). `@carbon/react-native` rows stay; they are IBM's Carbon Mobile. |
| 6 | Superset beyond Carbon | Added from `@carbon/ibm-products`: `Tearsheet`, `Card` (productive and expressive), `PageHeader`, `EmptyState` with variants, `FullPageError`, `NotificationsPanel`, `EditInPlace`, `ActionBar`, `TagSet`, `TagOverflow`, `RemoveModal`, `Saving`, `ScrollGradient`. Added without a Carbon reference: `Divider`; `FloatingActionButton` (composed; the roster notes Carbon's own answer is `BottomToolbarPrimaryAction`); `Carousel` (paged scroll plus dots); Button kinds `tonal` and `elevated`. Everything else in `ibm-products` is out of scope until added as a roster row. |
| 7 | Visual truth | No human in the loop. Five machine layers decide: structural assertions on the rendered DOM, measurement against the upstream reference, perceptual diff, accessibility tree identity, and pixel-exact regression baselines in the pinned Linux container. A human report becomes a new automatic check, never a one-off fix. |
| 8 | Verification cost | Three speeds: `check` after every edit (lint, purity, this component's tests), `batch` every eight to twelve components (full unit suite, browser gates for the batch, measurement, screenshots, docs regeneration), `verify` at milestones (clean installs, entire suite, fire runner, container baselines, native gate). Two execution tiers, no middle tier: a reasoning tier authors and decides, an execution tier runs and reports. |
| 9 | Session reading | Whoever authors a component reads a fixed briefing pack only: this file, the batch's roster rows, `docs/authoring.md`, `behaviors/ROBOTS.md`, one exemplar folder, the current defects list and the contact sheet. Never raw logs, never history. |
| 10 | Relationship to the previous library | Two brand-new repositories with clean history. Proven pieces of the previous library were copied as files; nothing was imported from it. The previous repositories are archived at launch. |
| 11 | Documentation | Every component doc page is generated from data at every batch close - props from `api.js`, tokens and enums from `spec.js`, behavior and accessibility from the behavior's declared data, platforms and provenance from the roster - and merged with a colocated `notes.md` written by the component's author in the same pass. Nobody edits a generated page. `notes.md` is vendor-free; vendor-related exceptions live only in the roster and are pulled into the page mechanically. A roster flag that demands an explanation (`deferred_gap`, `no_reference`, `web_only`, `requires_parent`) fails the build when `notes.md` does not mention it. |
| 12 | Native evidence | iOS and Android are observed on simulators in GitHub Actions at every milestone: an in-app walker renders the whole roster under every template, reports render errors, console errors, loaded fonts and measured layout, and uploads screenshots. Simulator evidence is stated as simulator evidence; real-device fidelity is a separate, later claim. |
| 13 | Icons | Icons are a token group in the themer contract (`icon.*`), each value an icon literal `{ icon: true, viewBox, paths, sizes? }` (the `icon: true` marker is the engine's convention for object-valued literals, as `shadow: true` and `spring: true` are), generated into each template from a pinned upstream set with recorded provenance. A brand overrides icons with a layer, like any other token. The renderer is `react-native-svg` on every platform, a peer dependency of this library; the `Icon` atom is the only icon knowledge the library holds and it never names a vendor. The `default` template carries Carbon's icon set; the Material template carries Material Symbols in the outlined style. No icon is ever silently substituted from another set. |
| 14 | Versions | Every package stays at 1.0.0 until launch under the delete-then-republish policy; at launch the contract version resets to 1 and real SemVer begins. |
| 15 | Templates | Exactly one template package per design system: `carbon`, `material`, `default`. Light and dark schemes live inside a template. A component that needs a token the contract lacks does not invent one: the request is queued in the workspace's `CONTRACT-REQUESTS.md` and applied at the next milestone as one contract bump, followed by regeneration and republication of every template in dependency order. |
| 16 | Where vendor knowledge lives | `carbon`, `material` and `ibm` appear in this repository only in `data/` (the roster, the icon table and their candidate inputs), `scripts/` (the roster and icon tooling that reads the pinned upstream packages), this file and `_test/`. The purity gate fails on any occurrence in what the package ships other than `data/roster.json`: `component/`, `behaviors/`, `components.js`, `all.js`, `README.md`, `ROBOTS.md`. Tests may name vendors because the measurement oracles import the upstream packages. |
| 17 | Framework modules | Nothing under `component/` or `behaviors/` imports `react`, `react-native` or `react-native-svg`. The host loader imports each once and injects it: `shared_libs.React`, `shared_libs.ReactNative`, `shared_libs.Svg`. `createSystem` reads them from there, the behaviors receive them through the composer, and `component/platform.js` is the one place `Platform.OS` is read. The library therefore shares the host's single instance of each framework, the test harness hands in the web builds without a module-resolution hook, and the purity gate can forbid the imports outright. |

## What the roster records

`data/roster.json` is the machine-readable companion of this file. For every upstream export it records the source package and version, the family, the tier, the behavior assigned, the platform answer, the reference used for measurement (or `no_reference`), the design-system twins where they exist, the deferred gaps, and the flags that force an explanation in the component's `notes.md`. A row is never deleted; an export that will not be built is marked with its reason.
